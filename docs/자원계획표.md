# 자원 계획표 — 계산치 vs 실측치 (과제 6)

**조건**
- 보드: Jetson Orin Nano Super 8GB, JetPack 7.2.1, 전력 모드 MAXN_SUPER, 호스트 실행(venv)
- 실측 기간: 12시간 가동 기간(2026-11-02 18:01 ~ 11-03 06:01)
- 같이 돈 것: 재실 인원 서비스, 키오스크 서비스, 시계열 추론 서비스(과제 8), InfluxDB 2개, MQTT 브로커
- 실측 출처: `results/service_logs/`(1분마다), `results/runs/pose_stats.csv`(1분마다), `results/service_logs/tegrastats.log`(1분마다)

## 1. GPU 예산 (1초당 GPU를 쓰는 시간)

| 작업 | 횟수/초 | 1회 시간 | 계산 GPU 점유 | 근거 |
|---|---|---|---|---|
| 재실 인원 (yolo11n PyTorch, 640) | 1 | 42.7ms (실측 평균, p95 48.1ms) | **4.3%** | 서비스 기록 `infer_ms_avg` |
| 키오스크 (yolo11n-pose PyTorch, 640) | 21.1 (실측 평균) | 약 25ms (같은 크기 yolo11n PyTorch 벤치마크 25.1ms로 추정) | **약 53%** | `pose_stats.csv` fps, `bench2.md` |
| **합계 (계산)** | | | **약 57%** | |
| 실측: 서비스가 1분마다 읽은 GPU 부하 | | | 평균 **68.6%**, 최대 99.7% | `service_*.jsonl` `gpu_pct` |
| 실측: tegrastats GR3D | | | 평균 **25.1%**, 최대 99% | `tegrastats.log` |

- 계산치(57%)는 서비스가 직접 읽은 값(68.6%)과 비슷합니다. 키오스크 영상 디코딩 뒤처리와 트래커가 더해진 만큼 실측이 조금 큽니다.
- tegrastats의 GR3D(25%)가 낮은 것은 1분에 한 번 찍는 순간값이라 추론 사이의 빈 시간에 걸리는 경우가 많기 때문으로 보입니다. **두 측정 방법이 다르므로 범위(25~69%)로 봅니다.**
- **TensorRT FP16으로 바꾸면**(과제 2 벤치마크: yolo11n 5.1ms) 키오스크는 21 × 약 6ms ≈ 13%, 재실 인원은 1%가 되어 **합계 약 14%**로 줄어듭니다. 지금은 두 서비스 모두 PyTorch로 돌고 있습니다.

## 2. CPU 예산

| 항목 | 계산 | 실측 |
|---|---|---|
| VIGI 서브 스트림(848×480) H.264 CPU 디코딩 | 1개당 약 9% (과제 1 연결 시험) × **2개**(두 서비스가 같은 카메라를 따로 받음) ≈ 18% | 보드 CPU 평균 **25.5%**, 최대 91.7% |
| 나머지 (전처리, 트래킹, 다른 서비스) | 약 5~10% | |

- Orin Nano에는 하드웨어 인코더가 없고, 이 보드의 OpenCV는 GStreamer 없이 빌드돼 있어 디코딩이 모두 CPU에서 일어납니다.
- **두 서비스가 같은 VIGI 영상을 따로 디코딩**하고 있습니다. 하나의 프로세스로 합치거나 한쪽이 디코딩한 프레임을 나눠 쓰면 약 9%를 아낄 수 있습니다(과제 6 심화 B).

## 3. 메모리 예산

| 항목 | 값 |
|---|---|
| 보드 전체 RAM | 7,486MB (+ 스왑 8GB) |
| 실측 사용 (tegrastats) | 평균 **4,056MB**, 최대 **6,957MB** |
| 실측 여유 (키오스크 `mem_avail_mb`) | 최소 **422MB** |
| 서비스 기록의 메모리 사용 | 평균 4,164MB, 최대 6,988MB |

- 최대 사용량이 7.0GB까지 올라가 여유가 0.4GB까지 줄어든 순간이 있었습니다. **이 상태에서는 로컬 LLM을 같은 보드에 올릴 수 없습니다.**
- LLM을 함께 돌리려면 PyTorch 모델 두 개를 TensorRT 엔진으로 바꾸고(프로세스당 수백 MB 감소 예상), 두 서비스를 한 프로세스로 합쳐 CUDA 컨텍스트를 하나로 줄여야 합니다.

## 5. 결론 — 카메라를 늘리면 무엇이 먼저 바닥나나

| 자원 | 지금 | 카메라 1대 추가 (같은 방식, PyTorch) | 판단 |
|---|---|---|---|
| GPU | 약 57~69% | +4% (재실 인원) ~ +53% (동작 인식) | 동작 인식을 하나 더 붙이면 **GPU가 먼저 바닥남** |
| 메모리 | 최대 7.0 / 7.5GB | 서비스 하나당 1GB 안팎 | **메모리도 거의 한계** |
| CPU | 평균 25% | 디코딩 +9% | 여유 있음 |
| USB 대역폭 | 웹캠 0대 사용 | MJPG 640×480이면 문제없음 | 여유 있음 |

→ 다음 단계의 우선순위는 **① TensorRT FP16 엔진으로 교체, ② 두 서비스를 하나로 합쳐 디코딩·CUDA 컨텍스트 공유**입니다.
